OBJECTIVE

Build QueueCutter, an AI paperwork copilot for government forms.

PRODUCT DEFINITION
QueueCutter turns confusing government paperwork into a guided conversation and produces:
1. a nearly ready-to-submit filled PDF,
2. a required document checklist,
3. a step-by-step submission guide,
4. warnings for missing, inconsistent, or risky answers.

MVP SCOPE
Build version 1 as a preparation layer only.
Do NOT integrate with live government systems.
Do NOT auto-submit to government portals.
Do NOT present the system as legally authoritative.
Do NOT claim official approval.

The application should let a user:
1. choose a form,
2. answer guided questions in plain language,
3. preview extracted field values,
4. download a filled PDF,
5. download or view a checklist,
6. see warnings and next-step guidance.

BUILD STRATEGY
Start narrow:
- support only 1–2 high-frequency forms,
- represent each form as a structured schema,
- map user answers to schema fields,
- generate the filled PDF and checklist,
- validate the result end-to-end.

If real official forms are hard to access or unreliable in the current environment, create legally neutral demo/sample forms that preserve the same workflow and structure so the product is still fully testable and demoable.

MANDATORY MVP FEATURE SET

QueueCutter version 1 must include:

A. Form selection
- Show a small catalog of supported forms.
- Each form must have title, description, who it is for, and expected documents.

B. Guided interview
- Replace confusing form fields with plain-language questions.
- Ask one question at a time or in small grouped steps.
- Allow edit/back navigation.
- Validate obvious formatting issues.

C. Structured mapping
- Convert answers into normalized form fields.
- Show which user answers mapped to which form fields.
- Handle missing and uncertain fields explicitly.

D. Preview
- Show a preview of the final field values before export.
- Highlight incomplete or suspicious entries.

E. PDF output
- Generate a downloadable PDF.
- If fillable PDF exists, fill it.
- If not, render a clean generated PDF reproducing the form structure sufficiently for demo and validation.

F. Checklist output
- Generate a checklist of required documents.
- Generate a step-by-step submission guide.
- Include warnings for likely rejection causes.

G. Warnings engine
- Detect missing answers,
- detect inconsistent answers,
- detect formatting problems,
- detect likely eligibility confusion,
- produce human-readable warnings.

H. Demo-ready UX
- The happy path must be clear enough for a live demo:
  choose form → answer ~8 questions → preview → download PDF/checklist.

QUEUECUTTER-SPECIFIC FUNCTIONAL REQUIREMENTS

The built app must include the following product behaviors:

1. Supported forms
- Build support for 1–2 forms only.
- Each form must be implemented as a schema-driven object.
- Each supported form must define:
  - display name,
  - short description,
  - required fields,
  - recommended supporting documents,
  - validation rules,
  - output field mapping.

2. Guided questions
- Questions must be simpler than the original form wording.
- Ask in plain language.
- Avoid bureaucratic phrasing.
- Use conditional branching where appropriate.

3. Mapping transparency
- User must be able to see what answers became what form values.
- If a field is inferred, label it clearly.
- If confidence is low or ambiguity exists, surface a warning.

4. Checklist logic
- Checklist must reflect the selected form and provided answers.
- Include “what to carry,” “what to verify,” and “what to do next.”
- Include missing-item warnings.

5. Warning logic
- Warn when:
  - required answers are missing,
  - values look malformed,
  - answers conflict,
  - output may be incomplete,
  - the user may need to confirm with the relevant office.

6. Output quality
- PDF must not be blank.
- PDF must contain expected field content.
- Checklist must not be generic filler.
- Submission guide must be form-specific.

7. Trust framing
- The app must clearly state that it helps prepare forms but is not an official filing authority.
- The disclaimer must not block usability, but it must be present.
